# Module 13 — Gestion des comptes internes (AGENT/REVIEWER/ADMIN)

> Permet à un ADMIN de créer, changer le rôle, désactiver et supprimer des comptes back-office (AGENT/REVIEWER/ADMIN) depuis l'UI, et permet à **tout compte** (y compris nouvellement créé) d'activer lui-même le MFA (TOTP) sur son propre compte. **Fait et déployé** (Lambda `users_api` dédiée, self-service MFA avec QR code dans `tenders_api`, email d'invitation et "mot de passe oublié" routés via SES avec domaine authentifié `optiprocure.pro`, longueur minimale du mot de passe 8).

## Objectif

`admin_create_user_config.allow_admin_create_user_only = true` (`cognito.tf`) désactive volontairement l'auto-inscription côté back-office — un compte AGENT/REVIEWER/ADMIN ne peut être créé que par une action administrative. Actuellement, cette action administrative n'existe **que** via AWS CLI/Console (c'est ainsi que les 3 comptes de test du module 03 ont été créés) : aucune route API, aucune UI. Ce module rend cette capacité utilisable par un vrai ADMIN métier, sans jamais lui donner d'accès AWS.

Deuxième volet, indissociable du premier : un compte fraîchement créé (par ADMIN, via ce module) n'a par construction pas encore de MFA activé, alors que CLAUDE.md l'exige pour toute action ADMIN sensible (approuver/rejeter/archiver, et par extension les actions de ce module lui-même) et le recommande pour AGENT/REVIEWER. Dans ce projet, l'activation du MFA de `test.admin` a été faite "à la main" via un script boto3 (`associate_software_token` → `verify_software_token` → `admin_set_user_mfa_preference`) — un contournement de test, pas une fonctionnalité produit. Sans un vrai chemin self-service, **tout** nouveau compte créé par ce module resterait bloqué sans MFA jusqu'à ce que quelqu'un exécute manuellement ce même script pour lui — ce qui ne passe pas plus à l'échelle que la création de compte elle-même.

## Décisions actées (tranchées avant codage)

Les trois points suivants ont été identifiés comme sous-spécifiés lors de la relecture de ce document (avant toute écriture de code) et sont tranchés ici — à ne plus rediscuter sauf découverte contraire en cours d'implémentation.

### 1. Effet du changement de rôle par un ADMIN

**Problème** : `resolve_role_from_groups` lit le claim `cognito:groups` du JWT forwardé par API Gateway. Ce claim est fixé au moment de l'émission du token (login ou refresh) — `AdminAddUserToGroup`/`AdminRemoveUserFromGroup` modifient l'appartenance aux groupes côté Cognito, mais un utilisateur déjà connecté garde son **access token actuel**, donc son ancien rôle effectif, jusqu'à son prochain refresh (jusqu'à 15 min, la validité de l'access token) ou sa prochaine réauthentification complète. C'est différent de `is_active`, relu en base à chaque requête via `require_active` — d'où un effet réellement immédiat pour la désactivation, mais pas pour un changement de rôle en l'état.

**Option (b) rejetée** : stocker un rôle "autoritaire" en DSQL, indépendant du claim du token, aurait nécessité de modifier `upsert_user` (déjà testé, déjà partagé par `tenders_api` et `reference_data_api`) pour qu'il cesse d'écraser `users.role` à partir des claims à *chaque* requête authentifiée — sans quoi le JIT provisioning re-écrirait l'ancien rôle dès la requête suivante et annulerait le changement fait en base. Ce changement toucherait un mécanisme central et déjà éprouvé pour un gain marginal, et introduirait deux sources de vérité pour le rôle (Cognito groupes vs DSQL) à réconcilier — complexité disproportionnée par rapport au besoin réel.

**Décision : option (a), avec `AdminUserGlobalSignOut`.** Un changement de rôle par un ADMIN déclenche systématiquement `cognito-idp:AdminUserGlobalSignOut` sur le compte concerné (révoque immédiatement tous ses refresh tokens actifs). Attention à ne pas surestimer l'immédiateté : l'**access token déjà émis reste valide jusqu'à son expiration naturelle** (15 min max, JWT stateless — API Gateway JWT Authorizer ne vérifie pas la révocation en temps réel, seulement la signature/l'expiration), donc l'ancien rôle continue de s'appliquer pendant cette fenêtre. Ce qui devient immédiat, c'est le **refresh** : `client.ts` rafraîchit proactivement 1 min avant expiration (`REFRESH_MARGIN_MS`), et cet appel à `/oauth2/token` échouera puisque le refresh token est révoqué — déclenchant le 401 déjà géré côté frontend (`clearTokens()` + redirection `/login`), qui force une reconnexion complète. Le compte récupère alors le nouveau rôle dès ce nouveau login. Fenêtre réelle avant effet garanti : jusqu'à ~15 minutes (durée de vie résiduelle de l'access token en cours), pas un blocage à la requête suivante — décision assumée, la "Définition de terminé" reflète cette fenêtre plutôt qu'une fausse promesse d'instantanéité.

### 2. Permissions IAM du MFA self-service (`tenders_api`, pas seulement `users_api`)

La leçon `docs/LECONS-APPRISES-AWS-SERVERLESS.md` §8 (tout appel `cognito-idp:*` depuis une Lambda exige une permission IAM explicite sur son rôle d'exécution, même quand l'action prend un identifiant/token utilisateur en paramètre) s'applique **aussi** aux routes `POST /me/mfa/setup`/`POST /me/mfa/verify`, qui tournent dans **`tenders_api`** (pas la nouvelle Lambda `users_api`, voir Périmètre). `AssociateSoftwareToken`, `VerifySoftwareToken` et `SetUserMFAPreference` sont chacune des appels `cognito-idp:*` distincts des actions `Admin*` déjà listées pour `users_api`. Décision : ajouter ces trois permissions au rôle IAM d'exécution de **`tenders_api`** (`infra/terraform/iam.tf`, `data.aws_iam_policy_document.lambda_tenders_api_policy` — le même bloc qui contient déjà `CognitoGetUser`), scopées à l'ARN du user pool, en plus (pas à la place) de `cognito-idp:GetUser` déjà présent.

### 3. Portée du user pool Cognito (liste des "comptes internes")

Confirmé par lecture de `infra/terraform/cognito.tf` : un seul `aws_cognito_user_pool` existe dans toute l'infra (`backoffice`), avec `admin_create_user_config.allow_admin_create_user_only = true` — aucune auto-inscription possible. Le commentaire en tête de fichier le confirme explicitement : "Le portail public n'a pas de User Pool ici : la création de compte abonné en libre-service (PRD §3.6) est un module applicatif séparé, à traiter avec sa propre logique métier". Les abonnés (module 08) n'auront donc **jamais** de présence dans ce pool — ce pool est structurellement exclusif au back-office.

Malgré cela, **décision : filtrer explicitement par groupe** (`ListUsersInGroup` sur `ADMIN`/`REVIEWER`/`AGENT`, ou `AdminListGroupsForUser` par utilisateur) plutôt qu'un `ListUsers` brut sur tout le pool, pour la route de listing des comptes internes. Raison : un `ListUsers` brut repose sur une invariante actuelle ("tout utilisateur du pool a forcément un groupe") qui n'est pas activement garantie par la structure des données elle-même — un compte créé sans être ajouté à un groupe (erreur d'implémentation future, ou création manuelle hors du flux de ce module) serait un compte "orphelin" sans rôle exploitable (`resolve_role_from_groups` renvoie `None`, refusé par `require_role`/`require_active` à toute requête) mais apparaîtrait quand même dans un `ListUsers` brut comme s'il s'agissait d'un compte back-office légitime. Filtrer par groupe reste correct même si cette invariante venait à être violée.

### 4. Suppression de compte : hard-delete Cognito + soft-delete DSQL

**Décision (ajoutée le 2026-08-07, demande explicite)** : `delete_account` appelle `AdminDeleteUser` côté Cognito (suppression définitive, pas de « corbeille » côté IdP — cohérent avec le fait que Cognito n'offre aucun mécanisme de restauration) mais ne fait **jamais** un vrai `DELETE` en DSQL — seulement `UPDATE users SET deleted_at = now()`. Raison : `tenders.created_by` et `audit_log.actor_user_id` référencent `users.id` sans FK (contrainte DSQL, voir CLAUDE.md) ; un vrai DELETE casserait silencieusement ces références historiques (un AO déjà créé/approuvé par ce compte doit rester attribuable après coup). Même garde-fou auto-action que le changement de groupes et la désactivation (`_reject_self_action`) : un ADMIN ne peut pas se supprimer lui-même. `list_accounts` filtre déjà `deleted_at IS NULL` — mais de toute façon un compte supprimé de Cognito n'apparaît plus dans aucun `ListUsersInGroup`, donc disparaît naturellement de la liste dès l'appel, indépendamment de ce filtre DSQL (défensif, pas strictement nécessaire).

### 5. Longueur minimale du mot de passe : 8 (pas 12)

**Décision (ajustée le 2026-08-07, demande explicite)** : `password_policy.minimum_length` passé de 12 à 8 dans `cognito.tf`. Pas une régression de sécurité disproportionnée compte tenu des autres exigences déjà en place et inchangées (majuscule, minuscule, chiffre, symbole tous requis) ; changement en place sur le user pool existant, sans impact sur les comptes déjà créés (la politique ne s'applique qu'aux nouveaux mots de passe définis, pas rétroactivement).

### 6. Livraison email : découverte que ce module dépendait d'un vrai correctif d'infra (SES)

**Découverte en vérifiant ce module** (pas une décision de conception, un bug d'infra réel qui bloquait `create_account` et le flux Cognito natif "mot de passe oublié") : `admin_create_user` n'indiquait pas `DesiredDeliveryMediums`, qui vaut `["SMS"]` par défaut chez Cognito — comme ces comptes n'ont jamais de numéro de téléphone, aucun email d'invitation ne partait. Corrigé en ajoutant `DesiredDeliveryMediums=["EMAIL"]`. Une fois corrigé, l'email partait bien mais atterrissait en spam (Cognito envoyait via `COGNITO_DEFAULT`, sans SPF/DKIM propres au domaine). Corrigé en configurant `email_configuration` sur `aws_cognito_user_pool.backoffice` (`cognito.tf`) pour router **tous** les emails du user pool (invitations `AdminCreateUser` **et** codes "mot de passe oublié" `ForgotPassword` — même configuration, un seul point de bascule pour tout le user pool) via Amazon SES, en s'appuyant sur `optiprocure.pro`, déjà entièrement vérifié dans SES (domaine + DKIM + accès production, hérité de la v1 d'OptiProcure, même région `ca-central-1`) — aucune nouvelle démarche DNS nécessaire. Vérifié empiriquement (pas supposé) : `ForgotPassword` sur un vrai compte Gmail retourne `CodeDeliveryDetails.DeliveryMedium = EMAIL`, et la métrique CloudWatch `AWS/SES Send` confirme l'envoi au moment exact de l'appel.

## Périmètre

**Dans le périmètre :**
- Route(s) API : lister les comptes internes (filtré explicitement par groupe Cognito — voir "Décisions actées" §3, jamais un `ListUsers` brut sur tout le pool), créer un compte (email + rôle initial), changer le rôle d'un compte existant (avec `AdminUserGlobalSignOut`, voir "Décisions actées" §1), désactiver/réactiver un compte, **supprimer un compte** (`AdminDeleteUser` + soft-delete DSQL, voir "Décisions actées" §4).
- Actions Cognito nécessaires côté Lambda `users_api` : `AdminCreateUser` (email d'invitation standard Cognito, mot de passe temporaire généré — pas de template custom dans cette première passe), `AdminAddUserToGroup`/`AdminRemoveUserFromGroup` pour affecter le rôle, `AdminUserGlobalSignOut` (révocation immédiate des tokens actifs après un changement de rôle), `AdminDeleteUser` (suppression définitive), `ListUsersInGroup` (ou `AdminListGroupsForUser`) pour le listing, permissions IAM correspondantes scopées au User Pool.
- Source de vérité de l'activation : `users.is_active` côté DSQL reste la source d'autorité effective (cohérent avec `require_active`, déjà en place et déjà vérifié à chaque requête via le JIT provisioning) — la Lambda synchronise Cognito en complément, jamais l'inverse.
- UI `frontend-admin` : nouvelle page "Utilisateurs" (ADMIN uniquement, même pattern de route protégée que `/referentiels`) — liste des comptes avec rôle/statut/MFA, formulaire de création, sélecteur de rôle, bouton activer/désactiver.
- **Self-service MFA** : route(s) API `POST /me/mfa/setup` (associe un secret TOTP, retourne le `SecretCode` pour affichage en QR code + saisie manuelle) et `POST /me/mfa/verify` (vérifie le code à 6 chiffres et active le MFA sur le compte appelant) — construites sur `GET /me` déjà existant, donc côté `tenders_api` (pas la nouvelle Lambda de gestion des comptes : ce sont des actions sur **son propre** compte, accessibles à AGENT/REVIEWER/ADMIN indifféremment, pas une capacité réservée à ADMIN). Permissions IAM `AssociateSoftwareToken`/`VerifySoftwareToken`/`SetUserMFAPreference` à ajouter au rôle d'exécution de **`tenders_api`**, pas `users_api` — voir "Décisions actées" §2.
- Page "Mon compte"/"Sécurité" dans `frontend-admin`, accessible à **tous** les rôles authentifiés (pas seulement ADMIN) : affiche le statut MFA actuel, propose l'activation (QR code généré côté client à partir du `SecretCode` — ex. via une lib légère de génération de QR, ou simplement afficher le secret en texte pour saisie manuelle dans l'app d'authentification, plus simple pour une première passe) et un champ de saisie du code de vérification.

**Hors périmètre :**
- Auto-inscription libre-service côté back-office — décision déjà actée (`allow_admin_create_user_only = true`), à ne pas remettre en cause.
- Emails transactionnels personnalisés (templates de bienvenue OptiProcure) — le mécanisme d'invitation standard de Cognito (email + mot de passe temporaire) suffit pour cette première passe.
- **Gestion du MFA d'un compte tiers par l'ADMIN** (le forcer, le désactiver, le réinitialiser pour quelqu'un d'autre) — seule l'**activation par l'utilisateur lui-même** est dans le périmètre (voir ci-dessus) ; un ADMIN peut seulement **voir** si MFA est activé sur chaque compte (déjà exposé côté `/me` via `mfa_enabled`, à étendre à la liste des comptes).

## Points à trancher avant de coder

1. **Lambda dédiée ou extension d'une Lambda existante ?** Même arbitrage que module 01 (`tasks/01-referentiels-admin.md` §"Points à trancher") : une Lambda séparée (ex. `backend/users_api/`) respecte le principe de responsabilité unique et isole le risque (permissions `cognito-idp:Admin*` ≠ permissions sur les AO/référentiels), au prix d'une duplication de `db.py`/`auth.py`. Recommandation par défaut : Lambda séparée si le volume dépasse ~200 lignes — à confirmer avec l'utilisateur au moment de coder.
2. **Un compte peut-il appartenir à plusieurs groupes Cognito simultanément ?** `resolve_role_from_groups` gère déjà la précédence (ADMIN gagne sur REVIEWER gagne sur AGENT) si un token porte plusieurs groupes, mais tous les comptes existants aujourd'hui n'ont qu'un seul groupe. Décider si l'UI de changement de rôle est un sélecteur simple (un seul rôle actif, le plus simple et le plus proche de la réalité actuelle) ou une sélection multiple — à trancher avec l'utilisateur avant de coder l'UI.
3. **Format de l'email d'invitation** : Cognito peut envoyer l'email de bienvenue automatiquement (`AdminCreateUser` sans `MessageAction=SUPPRESS`) ou la Lambda peut le supprimer et gérer sa propre notification (cohérent avec un futur système d'email applicatif, mais rien de tel n'existe encore dans ce projet) — commencer par l'envoi automatique Cognito (pas de sur-ingénierie), révisable.
4. ~~Rendu du QR code côté self-service MFA~~ — **tranché le 2026-08-07** : les deux options ensemble (QR **et** texte brut), pas l'un ou l'autre. QR généré entièrement côté client via la lib `qrcode` (npm) à partir d'une URI `otpauth://totp/...` — **jamais** via un service tiers de génération de QR, ce qui enverrait le secret TOTP en clair à un serveur externe. Le texte brut reste affiché en complément (accessibilité, copier-coller si le scan échoue).
5. **MFA recommandé (AGENT/REVIEWER) devient-il obligatoire au premier login ?** CLAUDE.md dit "recommandé" pour AGENT/REVIEWER, pas obligatoire — décider si la page "Sécurité" se contente d'être disponible (statu quo, cohérent avec le mot "recommandé") ou si un bandeau/rappel incite activement un compte sans MFA à l'activer — pas un blocage, juste une question d'UX, à trancher avec l'utilisateur.

## Définition de "terminé"

- Un ADMIN authentifié (MFA actif) peut créer un compte AGENT, REVIEWER ou ADMIN depuis l'UI, sans jamais passer par AWS CLI/Console.
- Le nouveau compte reçoit ses identifiants (email Cognito standard) et, dès sa première connexion, le provisioning JIT déjà en place (`auth.py::upsert_user`) lui attribue automatiquement le bon rôle et les bonnes `available_actions` — aucun changement requis côté provisioning.
- Un ADMIN peut changer le rôle d'un compte existant ; son refresh token est révoqué (`AdminUserGlobalSignOut`), donc son access token en cours reste valide jusqu'à ~15 min (durée de vie résiduelle), puis son refresh automatique échoue et le force à se reconnecter — il obtient alors le nouveau rôle. Pas un effet à la requête suivante, un effet garanti sous ~15 min maximum (voir "Décisions actées" §1, décision assumée, pas un défaut à corriger plus tard).
- Un ADMIN peut désactiver un compte ; l'utilisateur désactivé reçoit un refus (`require_active`, déjà en place) dès sa prochaine requête, sans attendre l'expiration de son token.
- Un ADMIN peut supprimer définitivement un compte (sauf le sien) ; le compte disparaît de Cognito (`AdminDeleteUser`) et de `GET /users`, la ligne DSQL est conservée en soft-delete (`deleted_at`) pour préserver l'historique déjà associé (AO créés, entrées d'audit).
- Un nouveau compte peut définir un mot de passe d'au moins 8 caractères (majuscule + minuscule + chiffre + symbole toujours requis) — vérifié en prod (`describe-user-pool`).
- Le flux natif Cognito "mot de passe oublié" (Hosted UI) envoie bien un code par email, livré via SES avec un domaine authentifié (SPF/DKIM `optiprocure.pro`) — vérifié avec un vrai compte, pas seulement supposé après le correctif d'envoi des invitations.
- **Un compte fraîchement créé par ADMIN peut, dès sa première connexion et sans aucune intervention CLI/script, activer le MFA (TOTP) sur son propre compte depuis la page "Sécurité"** — reproduit en self-service ce qui a été fait manuellement pour `test.admin` dans ce projet (`associate_software_token` → saisie du code → `verify_software_token`/`SetUserMFAPreference`).
- Un ADMIN nouvellement créé, une fois son MFA activé en self-service, peut immédiatement effectuer les actions qui le requièrent (approuver/rejeter/archiver un AO, créer/modifier un autre compte) — plus besoin qu'un opérateur exécute un script pour lui.
- Tests unitaires niveau 1/2 sur les permissions : seul ADMIN + MFA peut créer/modifier/désactiver un compte, jamais AGENT/REVIEWER (même pattern que les tests existants de `reference_data_api`) ; le self-service MFA, lui, est accessible à tout utilisateur authentifié sur son propre compte uniquement (jamais sur le compte d'un tiers, même pour un ADMIN).
